## 1. 开源究竟有什么意义

**源码可见不等于开放许可；免费不等于开源；开源也不等于放弃版权。** 开源许可证是在保留权利主体的同时，公开授予他人使用、复制、修改、分发等权利并规定条件的契约安排。OSI 的开源定义强调允许自由再分发、提供源码、允许衍生作品以及不歧视商业用途等要求。[OSI 原始定义](https://opensource.org/osd)；[GitHub 许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)。

为什么值得做：

- **个人与社区**：让复用路径合法、标准透明、外部可提出可验证改进；积累公开作品与技术信用，但不能把 Star 数直接当产品质量。
- **工程团队**：不必重复造轮子；通过评审、测试、Issue、SBOM/依赖目录把升级和追责从个人记忆变成流程。
- **企业**：提升互操作与采购选择空间；但引入第三方代码就引入许可义务、漏洞和出口/专利/供应链等潜在问题。
- **商业价值**：开源不排斥收费；可以围绕托管、支持、集成、服务建立商业模式。OSI 认可商业用途是开源的组成部分。

需要分别问：①“我们是否拥有公开授权的权利？”②“别人可以在什么条件下复用？”③“我们能否按许可证、合约和安全要求交付？”这三件事不能由“仓库 Public”推导。

## 2. 版权、许可、商标和商业秘密

| 概念 | 管什么 | 常见误区 | 检查动作 |
|---|---|---|---|
| 著作权 Copyright | 原创代码、文档、图像等受保护表达及相关权利 | GitHub 公开就丧失著作权 | 查作者、委托/雇佣/贡献协议和素材来源 |
| 开源许可证 License | 权利人允许第三方行使哪些权利、附什么条件 | README 写 MIT，根目录却另有不同许可，仍可任意用 | 核对真实 LICENSE 文本、适用范围、版本、例外 |
| 商标 / 品牌 | 名称、Logo、来源识别与品牌使用 | 源码 MIT 就能无条件使用项目商标 | 商标使用政策另行说明，避免误导为官方或背书 |
| 专利 | 技术发明及专利许可、诉讼条款 | 允许复制代码就自动授予全部专利权 | 尤其查看 Apache-2.0 / GPLv3 相关专利条款 |
| 商业秘密 / 隐私 | 未公开业务信息、代码、凭据、个人资料 | 删除文件或改私有就清除了历史泄漏 | 发布前扫描当前树、提交历史、第三方部署和缓存 |
| 合同 / 就业关系 | 权利归属、保密、竞业与授权流程 | 下班写的代码必然属于个人 | 根据合同、工作职责、设备与未公开资源逐案核查 |

对于中国法律关系，可阅读 2013 年修订《计算机软件保护条例》：其中第十三条列明若干在职开发软件著作权归属法人的情形，著作权许可和转让也有相应条款。不能仅凭“周末完成”“私人 GitHub 账号”直接认定为个人作品。原文：[中央网信办转载的条例](https://www.cac.gov.cn/2013-02/08/c_126468744.htm)、[最高法知识产权法庭](https://ipc.court.gov.cn/zh-cn/news/view-407.html)。其他司法辖区、劳动及委托合同应另行判断。

**四个不同对象分别决定授权**：自己原创代码、自己原创文章、第三方依赖、截图/字体/图片/商标。不要企图用仓库根目录一个 MIT 对所有内容一键授权。

## 3. 许可证速查与选择

以下仅是**典型原则和触发因素摘要**，不构成法律上的全面兼容性结论。见 [Choose a License](https://choosealicense.com/licenses/) 和 [SPDX License List](https://spdx.org/licenses/)；审阅真实条款时必须确认许可证的精确版本。

| 类型 | 常见标识 | 核心关注 | 适用思路 |
|---|---|---|---|
| 宽松 | `MIT` | 允许商业使用、修改和再分发；保留原版权及许可声明；不要求下游整体开源 | 通用工具库、个人 CLI、样板项目 |
| 宽松 | `Apache-2.0` | 除保留通知外含明确专利授权、修改说明及 `NOTICE` 条款；商标不当然授权 | 工程平台、可组合 SDK、公司协作 |
| 文件级回馈 | `MPL-2.0` | 修改 MPL 许可文件再分发的开源义务，组合与边界需逐案分析 | 希望改进回馈但允许与其他文件组合 |
| 库级回馈 | `LGPL-3.0-only` | 主要聚焦被许可库及修改；链接、替换/重链接条件需看细节 | 共享库（要审具体使用方式） |
| 强回馈 | `GPL-3.0-only` | 分发满足相应条件时提供对应源码并维持适用许可，链接/衍生作品判断复杂 | 希望发布衍生软件时保持开源 |
| 网络交互 | `AGPL-3.0-only` | 在 GPL 基础上，修改版通过网络向用户提供服务可能触发提供源代码的条款 | 网络服务中的强回馈主张 |
| 内容 | `CC BY 4.0` | 署名、许可链接、标明修改；允许商业使用 | 许可明确的原创教程、图文 |
| 内容 | `CC BY-SA 4.0` | 上述署名要求，且改编作品通常需同方式分享 | 希望知识衍生继续开放的文档 |
| 无明确许可 | `NOASSERTION` / 无 LICENSE | “可看”并不等于“可复制、改编、商用”；`NOASSERTION` 也不是许可证 | 待授权资产先只链接，不镜像、不打“开源”标签 |
| 专有 | 商业许可 / 内部条款 | 权限来自书面约定或平台服务条款，不应称 OSI 开源 | 内部工程、客户专属交付、双许可商业产品 |

**重要区别**：

- “可以商用” ≠ “无需署名/不留许可文件”；例如 MIT 也要求保留版权与许可声明。
- “GPL 一定会把公司所有代码传到网上”是过度简化；是否发生分发、链接和衍生作品关系、权利边界、GPL 版本、例外及合同条款都要考察。单纯私有使用与对外交付不同。
- “SaaS 一律不触发开源义务”同样错误：需要特别检查 AGPL 等网络交互条款。
- Creative Commons **不推荐**将 CC 许可证用于软件源码，推荐改用软件许可证；CC 可用于独立文档与美术资源。[CC 官方 FAQ](https://creativecommons.org/faq/)。
- `AND`、`OR`、`WITH` 等 SPDX 表达式有明确语义；不要把文件中多条许可证简单视为“任选一个”。[SPDX expressions](https://spdx.github.io/spdx-spec/v2.3/SPDX-license-expressions/)。
- “双许可”不是同一份文档同时出现两个不兼容声明；要有明确哪些版权持有人授权、适用哪些代码、接收者是否有选项等法律依据。

### 选择决策树

1. 我们**拥有全部相关权利或拿到了再授权许可**吗？否：停止公开授权，先补权属证据。
2. 这是**代码**还是文章/视觉内容？代码优先评估 OSI 认可的软件许可证；内容按权属评估 CC，二者分界写进仓库。
3. 期望别人将项目集成进闭源商业产品吗？如果希望尽量容易集成，通常先比较 MIT / Apache-2.0；如果希望修改回馈，再评估 MPL / LGPL / GPL / AGPL。
4. 是否包含他人代码、模型权重、数据集、字体、商标、截图或受限制的 API？逐项核对其原授权，并进行兼容性和分发义务审查。
5. 公司是否采用了批准的许可证清单、代码贡献政策、法务审批/例外流程？没有先建立流程，不应靠个人偏好直接定公司仓的许可证。

## 4. 个人、团队、公司三种使用场景

### A. 个人版 / 个人作品

- 明确仓库是否个人原创、是否包含雇主或客户资源；保留原创来源与授权证据。
- 代码可优先考虑 MIT 等简洁许可；文章、Logo、截图分开标注。
- 公开前确认 `README`、`LICENSE`、`SECURITY.md`（涉及安全报告时）与实际内容一致；不要用“生产验证”“零成本”等不可证明表达。
- 后续版本可修改新版本的许可决策，但**不能单方面撤回别人已经合法取得的既有授权**；历史贡献者版权不因改一个 LICENSE 文件自动属于维护者。

### B. 小团队共建

- 项目 Owner 决定目标与许可方案；贡献者确认其对贡献拥有权利。
- 选择并说明 DCO（`Signed-off-by`，自我声明贡献来源）还是 CLA（额外签署贡献授权），二者不是同一回事；未获授权的公司员工贡献应走公司流程。
- 明确 PR 门禁：许可证/依赖变更、SAST、Secrets、测试、至少一次授权审查、可回滚；不要只靠 PR 合并按钮是否为绿。
- 对安全修复实施隔离披露；公开安全报告前先给维护者私密通知渠道。

### C. 企业生产 / 对客户交付

- 用**入口—审查—使用—发版—更新—退役**的完整台账管理开源组件。采购方、供应商、外包、员工贡献与第三方素材都应纳入范围。
- 至少记录：组件名、版本、来源 URL/校验和、许可证及表达式、分发/托管形式、是否修改、直接/传递依赖、开源声明/NOTICE、漏洞状态、使用 Owner、审批单、应急替代路线。
- 区分三种活动：内部运行；对客户发二进制、容器、SDK 或设备；对外提供在线服务。三者可能承担不同的许可义务。
- 对无法确认兼容性的 GPL、AGPL、LGPL 组合，以及专利/商标/跨境/雇佣权属问题，建立**法务或合规负责人批准**，不能让 Agent 自动批准。
- OpenChain ISO/IEC 5230 是开源许可证合规**流程标准**；ISO/IEC 18974 是开源安全保障**流程标准**，它们不是某个具体许可证的解释，也不替代法律咨询。[OpenChain 官方介绍](https://openchainproject.org/get-started)。

## 5. 使用第三方依赖的合规闭环

`发现组件 → 验证来源 → 明确用途与分发方式 → 扫描许可证/SBOM → 审核兼容性 → 记录 NOTICE/源代码义务 → 测试 → 放行 → 周期复核`

**最小台账字段（可复制成 CSV 列）**：

`repository, component, package, version, source_url, source_sha, declared_license, detected_license, license_expression, rights_owner, usage_mode, distributed, modified, notice_required, source_offer_required, vuln_id, vuln_status, upgrade_target, reviewer, decision, evidence_url, verified_at`

实践注意：

- **扫描器报告不是许可证裁决**：可能漏掉子目录、生成代码、 vendored copy、图形字体与依赖的真实许可范围。异常必须读源文件和上游文本。
- **SBOM 是清单，不是合规证明**。SPDX/CycloneDX 用于标准化资产与组件事实；企业仍需完成授权、使用方式和发布义务判断。
- 预编译二进制、Docker 镜像、模型/数据集与外部 CDN 都有权利及安全边界，不能只扫描顶层包管理器。
- 仓库 README 中的许可证徽章、GitHub 自动识别结果、`LICENSE`、文件 SPDX 标头不一致时标记 `LICENSE_CONFLICT`，先保持原状，询问权利人并独立复核，不机械覆盖。
- 使用固定版本/提交 SHA、保留构建来源、测试和回滚记录；这不自动消除上游供应链风险。

## 6. 安全漏洞与升级工作流

从“定期更新依赖”升级为“有风险分级的修复交付”：

1. **发现**：Dependency Graph / Dependabot alerts、上游安全公告、GitHub Advisory Database、OpenSSF Scorecard、SCA/SAST/secret scanning。
2. **确认**：组件、受影响版本、真实运行路径、可利用性、环境暴露、严重度及业务影响；无法确认应标 `unverified`，不是“安全”。
3. **冻结证据**：锁定原依赖版本、补丁候选、SBOM 版本、漏洞 ID（CVE/GHSA）、是否公开、测试基线、决策人、回退方案。
4. **最小修复**：优先安全补丁版本、隔离危险功能、限制网络入口或替换依赖；不要仅因“最新”就盲升级主版本。
5. **验证**：自动测试、关键功能回归、许可再次检测、构建与镜像扫描、必要时灰度和人工验收。
6. **部署与回退**：生产部署须经过授权；如真实风险升高、回归失败、组件许可证变化或供应商来源不可信，立即阻断并恢复稳定版本。
7. **留痕**：PR、证据链接、实际执行命令、测试结果、批准人、发版 SHA、关闭漏洞的证据。未执行的写 `NOT_RUN`。

GitHub 的 Dependabot security updates 可以为可修复的受影响依赖提出 PR，但“产生 PR”不等于“测试通过/可自动合并”。[GitHub 供应链安全](https://docs.github.com/en/code-security/concepts/supply-chain-security) · [Dependabot](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependabot-security-updates) · [OpenSSF Scorecard](https://openssf.org/projects/scorecard/)。

**特别注意**：安全升级时也可能发生许可证变化、弃用、二进制制品来源变化、恶意包替换、Breaking Change，故“安全补丁”和“权利审查”需要在同一个 PR 门禁里。

## 7. 常见误解、边界和决策问题

| 常见说法 | 更准确的判断 |
|---|---|
| “开源就是无版权” | 著作权通常仍存在；许可证明确条件 |
| “公开仓默认允许任何商业复用” | 缺许可证时一般不自动获得复制、修改、分发权 |
| “MIT 不需要保留任何署名” | MIT 要求保留版权和许可声明 |
| “有 CC BY-SA 徽章等于实际授权” | 必须核对权利人、LICENSE 文本、适用范围与素材权属 |
| “把公司项目脱敏就能作为个人开源” | 脱敏不能解决权属、商业秘密、合同或授权问题 |
| “GitHub Actions 绿灯等于无安全漏洞” | 工具只能检查其覆盖范围；部署与回滚仍需审查 |
| “AGPL 和 GPL 都只在卖软件时触发” | 具体分发和网络服务条款不同，不能按是否收费分类 |
| “发布新许可证可以消灭旧版授予的权利” | 已依法取得的既有授权不能简单被后续改文件撤回 |
| “一个扫描器没有问题就合规” | 扫描、权属、许可、履约、更新和实际交付是不同门禁 |

### 给管理者的五个追问

- **权属**：谁有权以本项目许可对外授权，第三方贡献和雇佣关系是否已核实？
- **使用**：我们的行为是看、运行、修改、内部分发、客户交付还是网络服务？
- **义务**：涉及哪些授权告知、署名、源代码、NOTICE、修改说明与专利条款？
- **安全**：哪些依赖在实际攻击面中暴露，多久能打补丁，失败怎么回退？
- **证据**：仓库、发布包、客户协议和审计报告各自留存哪个不可伪造的版本与审查记录？
