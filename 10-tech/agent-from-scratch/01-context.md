# 01 · 上下文：Agent 的第一块地基

## ① 这一层解决什么问题

很多人以为 Agent 是模型本身。不是。模型只是那个被喂上下文、吐回复的黑盒。Agent 真正的东西，是「围绕模型组装起来的那段上下文，加一个循环」。地基不稳，后面循环再花哨也白搭。

这一层要回答的是：模型一次推理，到底看到了什么？最朴素的情况，上下文只有两样东西——系统设定（你是谁、不能做什么）和用户这句话。把这两样拼起来丢给模型，就是一个能聊天的 bot，但它做不了任何「要碰外部世界」的事：你问它「查我下周三的日程」，它只能回「我没法读取你的日历」。

为什么做不到？因为模型本身不会执行代码、不会查库。它唯一能做的，是基于你给的上下文做下一句预测。所以「让它干活」的第一件事，不是换更强的模型，而是把干活要用的东西塞进上下文。这一步做对了，后面四篇才有意义。

## ② 最小代码：五版进化（地基在 V1/V2）

```python
# V1 两行：上下文 = 系统设定 + 用户输入，直接给模型
ctx = system_prompt + user_input
reply = model(ctx)                      # 模型没有工具，答不了"查日程"

# V2 五行：把工具协议和工具集也塞进上下文
ctx = system_prompt + user_input + tool_protocol + tool_set
req = model(ctx)                        # 模型可能回："我要调 get_calendar"
if req.is_tool_call:
    result = run_tool(req)              # 承接工具请求、执行
    ctx = append_context(ctx, result)  # 心脏：结果必须写回上下文
    reply = model(ctx)                  # 拿着结果二次推理
print(reply)

# V3 while True：把重复的工具执行抽成循环（详见 04-loop）
# V4 工具协议：上下文里只放"名称/解决什么/输入"，不放源码（详见 03-tools）
# V5 skill_catalog：Skill 也变成可查询的协议（详见 04-loop）
```

V2 多出来的三行，关键不在「调了工具」，而在 `append_context`——工具跑出来的结果必须写回上下文，否则下一轮模型根本看不到，等于白跑。梁凯锐在现场把这一步叫整个五版代码的心脏。

## ③ 现场原话转述

## ④ 我的理解

这部分基本是现场新学的，但我自己此前有一个判断被它接上了：上午场我独立得出「除模型外皆 Harness」——上下文的拼装、工具协议、结果回写，全都属于 Harness。梁凯锐这段代码正好把「Harness 是什么」落到一行行代码上：原来 Harness 不是某个框架，而是「你怎么把模型要的东西喂进上下文、又把结果接回来」这件事本身。

我此前已知的是：上下文工程在 2024 年就成了独立话题。但我是第一次把「上下文拼装」和「Agent 地基」这么直接地对应起来——之前我把它当成 prompt 技巧，现在它是一等公民，循环、工具、Skill 都是往这块地基上长的。

## ⑤ 可复用产物：上下文拼装清单

写任何 Agent 前，先用这张清单核对上下文里有什么：

- 系统设定：身份 + 明确「不能做」的边界
- 用户输入：本轮真实问题
- 工具协议：有哪些工具、各自解决什么、要什么输入
- 历史：已执行的工具结果（必须写回）
- 缺失任一项，先在 V1/V2 阶段补齐，别急着上循环

## ⑥ 待验证 / 我不确定的地方

- V2 这种「写死两次模型调用」的写法，现场是为了演示，真实工程一定会进 while，但两阶段写法的边界在哪、什么时候必须切循环，我还没亲手测过。
- 「append_context 是心脏」是现场强调，我在自己小模型上还没复现过「不写回就答错」的失败样例，准备本地跑一次对照。
