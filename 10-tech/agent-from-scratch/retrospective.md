# 复盘：点亮第一个 Agent 这条线

## 听之前我以为 Agent 是什么

入场前我对 Agent 的认知是「一个会调工具的 LLM 外加一段提示词」。我能背出 ReAct，能说出 function calling，也能讲框架大概怎么用。但我的认知是断的：模型、工具、循环这三块各知道一点，拼不出一条连贯的因果链。尤其模糊的是——「决策到底在谁手里」「Skill 是怎么进上下文的」这两件事，我答不上来。

说白了，我处在「能聊概念、不能画全链路」的阶段。

## 听完之后改了什么认知

改得最彻底的是一句话：Agent 不是模型，是「围绕模型组装的上下文 + 一个 while 循环」。模型只是被喂和被吐的黑盒，真正值钱的是那段拼装和那个循环。

顺着这个，两个以前半懂不懂的点清楚了：
- 决策权在哪。加 while 之前，走几步是程序写死的；加了之后，模型自己判断「还要不要调工具、什么时候停」。这一行 while 就是 Agent 和 chatbot 的分界线。
- Skill 怎么进上下文。不是全预载，是平时只留查询入口，用到才 load 进 .md 正文。渐进式加载既省 token 又避免 Skill 打架。

更深一层，我把这条链和我上午场的判断对齐了：「除模型外皆 Harness」——上下文拼装、工具协议、结果回写、循环、加载，全是 Harness；「把 Harness 封装成 Skills」——V5 的 search/load_skill 就是它的工程落地。上午我先想到，下午被整场验证，这条线现在是闭环的。

## 哪些地方我当时没跟上

- 郭美青的 HE 六层我是听到了，但当时只记住了名字，没及时和梁凯锐的代码对上「任务约束层 = system_prompt 边框」这层关系，是回头整理时才接上的。
- 产品经理那段 Skill 打架，现场听着像闲笔，后来才意识到它是 Harness 工程的真复杂度——Skill 不是越多越好，治理冲突是独立课题。
- 八框架同一内核那页，现场一闪而过，我还没做成对照表，属于「知道结论、没吃透」。

## 接下来要补什么

1. 本地用一个小模型把五版伪代码真实跑通一轮（差旅查询场景），重点复现「不写回上下文就答错」和「while 让多步任务跑通」。
2. 实测 Skill 渐进加载的 token 节省量级，核实「几百个 Skill 只花 1 个 search token」的说法。
3. 就 Skill 冲突治理做一轮小实验：关无关 Skill / 打包成工作流插件，看哪条更顺手。
4. 把「除模型外皆 Harness → 封装成 Skill」落成我自己素材处理助手的可见模板，先做一个再扩。
5. 补一张八框架对照表，验证「模型+工具+边界=同一副基座」是否经得起逐个框架核对。
