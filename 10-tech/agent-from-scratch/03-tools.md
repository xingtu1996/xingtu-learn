# 03 · 工具：工具协议与外部世界

## ① 这一层解决什么问题

前两篇模型已经有了上下文和推理节奏，但它还是关在盒子里的——不会真的去查日历、订票、读文件。要让它碰外部世界，得给它工具。

关键认知：模型没有代码执行能力，你不能把一整段源码塞进上下文。你能塞的，是对工具的「协议」——一份说明书写给模型看：有什么工具、各自解决什么、要什么输入。模型读完协议就知道该请求哪个工具，真正的执行由你的程序用代码承接。这一步把「能力」翻译成了「模型可读的说明书」，是 Agent 连接真实系统的接口层。

还有一个容易混的点：工具和 Skill 不是一回事。工具是代码执行（程序里真跑一段逻辑），Skill 是一份 markdown 文档（加载进上下文让模型按指令工作）。本篇讲工具，Skill 留到 04。

## ② 最小代码：五版进化（工具在 V2/V4）

```python
# V1 两行：无工具
ctx = system_prompt + user_input
reply = model(ctx)

# V2 五行：把工具协议塞进上下文，程序承接执行
ctx = system_prompt + user_input + tool_protocol + tool_set
req = model(ctx)
if req.is_tool_call:
    ctx = append_context(ctx, run_tool(req))
    reply = model(ctx)

# V4 工具协议：上下文里只放"说明书"，不放源码
tool_protocol = [
    {"name": "get_date",     "solves": "把'下周X'转成具体日期", "input": "weekday"},
    {"name": "get_calendar", "solves": "查某人某天日程",        "input": "date"},
]
# 模型读到协议就发起请求；程序按 name 找到真实函数执行
def run_tool(req):
    return TOOL_IMPL[req.name](req.input)

# V3 while True：让上面的请求可重复（详见 04-loop）
# V5 skill_catalog：Skill 也变成可查询协议（详见 04-loop）
```

V4 的改动很小但很重要：上下文里不再出现任何源码，只有三要素——名称、能解决什么、要什么输入。模型不需要懂实现，只要懂「何时该叫它」。

## ④ 我的理解

「工具协议 = 把能力变成模型可读的说明书」是我现场新抓到的表述，但它正好落地了我上午场的判断 F8——「把 Harness 直接封装成 Skills」。工具协议是 Harness 的一种最小形态：你不改模型，只是给它一份能调用的说明书。区别在于工具跑代码、Skill 读文档，但两者本质都是「往上下文外挂一份可控的能力描述」。

我此前已知的是 function calling 的基本机制，但没把它和「Harness 即控制手段」这么清楚地连起来。现在我看任何 Agent 框架，第一眼先找它的「协议层」长什么样——这层才是真功夫，框架外壳反而是会变的。

## ⑤ 可复用产物：工具协议模板

```json
{
  "name": "get_calendar",
  "solves": "查询指定人员某天的日程，返回空闲时段",
  "input": { "date": "YYYY-MM-DD", "person": "string" },
  "note": "只返回事实，不替用户做任何预定动作"
}
```

写工具时先填这份协议，再写 `TOOL_IMPL` 里的真实函数。协议描述越清楚，模型调错的概率越低。

## ⑥ 待验证 / 我不确定的地方

- 协议描述写到多细模型才不会调错？太粗模型乱猜，太细又占上下文。这个平衡我没测过，标待核实。
- 工具粒度过细（一个动作一个工具）还是过粗（一个流程一个工具）更省心，现场没给结论，等我实跑后补。
- 工具与 Skill 的边界：哪些能力该做成代码工具、哪些该做成文档 Skill，我目前只有模糊直觉，需要更多案例校准。
