## 二、三个我没想到的地方

### 1. 循环在第 02 幕，不在最后

我的顺序是「上下文 → 提示词 → 工具 → 循环」，把循环当压轴。真实顺序里 while 出现在第 02 幕，远早于 System Prompt（03）和工具协议（04）。

回头想，这个顺序更对。**循环是 Agent 的定义性特征**——没有循环，前面堆再多提示词和工具也只是"会调一次工具的聊天机器人"。先把循环立起来，后面每一幕都是在同一个循环上换内容、加约束。我把它放最后，等于把骨架当成了装修。

这也正好呼应我上午自己推导的那句判断：本质模型控制，其他皆 Harness。循环就是那个控制权移交点，它该在最前面。

### 2. 第 01 幕故意留了个缺陷

第 01 幕的代码里，如果模型在第二次响应里又提出工具请求，程序**不执行**它，只发一个 `unhandled_tool_request` 事件就停了：

```python
next_response = run.call_model(context)
if next_response.tool_call:
    # 第二个动作只是请求，没有执行它，也不能标记成功
    run.emit('unhandled_tool_request', request=next_response.tool_call)
    run.status = 'unhandled_tool_request'
```

注释写得很直白：「第二个动作只是请求，没有执行它，也不能标记成功」。

这是教学上的狠招：**先让你亲眼看见单次调用在哪里断掉，再在第 02 幕给 while。** 我写第 01 篇时只讲了"单次调用不够用"，是抽象结论；人家是让你跑一遍看它断在哪。差距在于，我的读者要信我的话，他的读者自己会疼。

### 3. 完成判定不看模型说什么

这几幕的 `is_complete` 从不问模型"你完成了吗"，而是查结构化状态：

```python
def is_complete(run):
    return any(e['type'] == 'tool_succeeded' and e['name'] == 'check_calendar'
               for e in run.events)
```

到 07 幕更直接，查 `run.toolbox.state.get('finalized')`——程序自己的状态位。

这一条我之前完全没意识到。模型嘴上说"已完成"是不可信的，得有一个它改不了的外部事实。这和我这半年做工程的体感一致：凡是让模型自己给自己判卷的地方，早晚会出事。

## 三、最值钱的部分：写进 System Prompt 的反幻觉约束

九幕的代码骨架其实很朴素，真正见功力的是每一幕 `prepare()` 里那段 `rules` 字符串。它不控制模型怎么想，只规定什么话不能说。摘录几条原文：

- 「不得把草稿称为已经提交或发送。」
- 「涉及差旅制度与额度，必须先用 search_knowledge 查询制度并保留来源，再估算费用和创建申请；不能用模型常识替代制度证据。」
- 「初始测试必须存在失败，最终三个测试全部通过。引用实际测试结果，不把未运行称为通过。」
- 「核对时间和口径，不能把历史数字称为现状。」
- 「不得补造数字。」
- 「工具返回素材不代表模型已看过图片。」
- 「不虚构审片结论。」

逐条看下来会发现一个共同点：**它们全在堵"模型把没做的事说成做了"这个洞。** 不是加能力，是加不许。

这直接印证了那句判断——模型负责生成，Harness 负责约束。而且约束的颗粒度细到"不许说没运行过的测试通过了"，说明作者是真被这类问题咬过。这几条我抄进自己的工程清单了。

## 四、两个安全设计

**Skill 分层门禁**：02 幕的 `tools_for()` 里有一行硬校验——

```python
if dynamic_skills:
    raise ValueError('动态 Skill 需要阶段6或以上')
```

能力按幕解锁，不能跳级。这和我做权限系统的思路一样：功能的可见性要跟着阶段走，不能一次性全给。

**不执行模型生成的代码**：08 幕的 `evaluate_amount()` 不是 exec 模型写的 Python，而是用 `ast.parse` 解析后只允许「一个函数、无循环、无导入、无任意调用」，超 2000 字符直接拒。注释写着「只解释极小 Python 子集，不执行用户源码」。

这是边界感。让 Agent 改代码和让 Agent 执行自己写的代码，是两件风险差一个数量级的事。
