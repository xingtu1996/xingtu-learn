# 文章草稿｜我给 AI 会话起了名字，才发现它们还缺一份“工作合同”

> 类型：行途工程实践分享 · 未发布 · 待核对 Work 最终结果  
> 素材：用户 2026-11-02 Work 实际操作截图，Library `/XSA_工程实践素材`。当前配图为待审核的局部截图，不要直接外部发布原图。

这两天在整理行途的开源项目，遇到一个非常具体的问题：ChatGPT 里讨论得很清楚的任务，切换到 Work、Muse 或 Codex 后，还是得重新解释一遍。

我原来以为，是提示词没有写完整。后来发现，问题不完全在提示词。

**不同会话其实承担着不同工作，但我们一直把它们当作同一种聊天窗口。**

于是我给会话做了个很朴素的约定：

- `XSA (chat)｜Super Agent 工程总控`，研究架构、做决策；
- `XF (chat)｜FDE 知识与工程实践`，研究知识体系与实践；
- `XF (work)｜FDE 工程建设`，负责实际建设仓库、提交文件、跑验证；
- GitHub 不负责聊天，负责保存任务、版本和证据。

这次实际操作中，我先在 Chat 形成 FDE 工程任务包，把主仓库、总控仓库、模型选择、验收要求和安全边界写清楚。随后新开 Work，选择 GPT-6.1 Sol、高推理强度，把任务交给它执行。

截图里的任务已经启动，但还处于执行和连接状态。我现在不会把它写成“AI 已经自动建好仓库”。

反而是在这个过程中，发现了一个更值得记录的小错误。

**会话列表里写着 `XSA (work)`，发给它的却是 `XF (work)` 的 FDE 任务。**

人看一眼大概能猜到，机器不该靠猜。

以后如果 XSA 真要自动调度多个 Agent，仅仅给聊天起名字肯定不够。还需要一份明确的工作合同，写清楚：

```text
Project: XF
Repo: xingtu1996/xingtu-fde
Role: FDE Engineer
Mode: Work
Output: Draft PR + Commit + Test Evidence
```

这个合同决定执行范围，GitHub 的 PR 和 Commit 决定完成证据。

由此我重新理解了我们一直说的“Super Agent”：它不一定是一个更强的单体 AI，也可能是一套让不同 Agent 按明确任务分工、交接、授权和验收的工作体系。

目前我只验证了**命名约定、任务包和 Work 启动**这一步。自动监听、跨产品消息回传、冲突保护还在研究。

这套尝试暂时归纳成一句话：

**Chat 负责规划与裁决，Work 负责工程实施，GitHub 负责状态和成果。**

真正要解决的不是聊天能不能无限延续，而是一个会话结束后，下一个 Agent 能不能拿到清楚的目标、接上正确的工作、交出可核验的结果。

这件事还没有做完，后续我会把遇到的冲突和失败也留下来。
