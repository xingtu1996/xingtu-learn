---

## 为什么单独开这个目录

自驱学习有个致命弱点：**它需要意志力，而意志力是最不可靠的资源**。

我试过"这周学点微服务治理"，结果通常是：第一天热情高涨，第三天开始忙，第二周彻底停摆。不是因为懒，是因为**没有外部力量在逼我**。

工作驱动的学习不一样：

- 有真实的问题在等你（不学就做不下去）
- 有明确的验收标准（做完能交付，而不是"感觉学会了"）
- 有 deadlines（项目不会等你）

所以这个目录记的是**被工作倒逼出来的学习**，它的完成率天然高于自驱线。

## 记录格式

每条工作驱动的学习记录包含五段：

```
1. 触发问题      —— 哪个项目、遇见什么具体障碍（脱敏后）
2. 需要学什么    —— 拆成可验证的具体能力
3. 时间预算      —— 这个项目允许我花多久（关键约束）
4. 学了什么      —— 笔记、最小验证、踩坑
5. 回到工作      —— 学完之后项目里怎么用的，效果如何
```

**第五段最重要**。没有"回到工作"这一环，这条线就退化成了普通笔记——而"用上了"才是工作驱动学习区别于自驱学习的根本。

## 一个提醒

工作驱动学习的**隐藏风险**是：只学当前项目用得上的东西，视野会越来越窄。

对策是定期问自己：

> 这个项目逼我学的东西，有多少在下一个项目里还用得上？

如果答案经常是"都用不上"，说明你在被项目牵着走，而不是在用项目练能力。

## 脱敏要求

本目录的记录来自真实工作项目，因此**必须遵守** [xingtu-portfolio 的脱敏规程](https://github.com/xingtu1996/xingtu-portfolio/blob/main/00-DESENSITIZATION.md)：

- 客户名 → 行业一级类目
- 项目代号、内部系统名 → 通用描述
- 人天、金额、规模 → 删除或量级化
- 同事姓名 → 角色代称

工作驱动不意味着可以把工作细节带进来。**写的是"这类问题要学什么"，不是"这个项目做了什么"。**
