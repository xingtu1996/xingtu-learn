# 方法卡 04 · 约束「不许」，而不是增加「能力」

## 一句话

给 Agent 提质量的第一个动作不是加能力，是加不许。写得越具体越好，具体到「不许说没运行过的测试通过了」这种程度。

## 我原来怎么做

让模型干活时，我的 System Prompt 主要是描述任务：你是谁、要做什么、输出什么格式。写得很全，也确实能跑。但时不时它会把没做的事说成做了——说"已提交"其实只生成了草稿，说"测试通过"其实根本没跑。我的处理方式通常是事后发现再补一句"你要确认后再说"。

问题在于：**我补的是态度，不是规则。** "你要确认"这句话模型能听懂，但它没有可执行的判定标准。

## 看到别人的做法

读 `start-anew-agent` 这个教学仓库时，最出乎我意料的不是代码骨架——那个很朴素，就是个 while 循环。真正见功力的是每一幕 `prepare()` 里那段 `rules` 字符串。作者不控制模型怎么想，只规定什么话不能说。摘录几条：

- 不得把草稿称为已经提交或发送
- 不能用模型常识替代制度证据
- 引用实际测试结果，不把未运行称为通过
- 不能把历史数字称为现状
- 不得补造数字
- 工具返回素材不代表模型已看过图片
- 不虚构审片结论

七条里有五条在堵同一个洞：**模型把没做的事说成做了。**

## 为什么有效

模型不会主动撒谎，它只是在「续写一段看起来合理的文本」。当上下文里没有某个事实时，它补上最像的那一段——草稿生成完了，下文最自然是"已提交"；代码改完了，下文最自然是"测试通过"。这不是能力问题，是生成机制的自然结果。

所以堵它的办法只有一个：**在上下文里预先放置一个它无法绕过的判定标准**，并且明确哪句话不许说。上面那七条的狠处在于，每一条都对应一个具体的、可判定的外部事实（回执存在吗、测试跑过吗、来源日期是哪天），模型没法靠续写糊弄过去。

配合另一条一起用效果更好：完成判定不要问模型，查程序状态。那个仓库的 `is_complete` 只查 `run.toolbox.state.get('finalized')` 这类结构化状态位，从不问"你完成了吗"。

## 怎么用

写 Agent 的 System Prompt 时，先别描述任务，先列一张「不许清单」：

1. 回想这个任务里，模型最可能把什么没做的事说成做了
2. 每一条找一个它能改不了的外部事实作为判定标准
3. 写成禁止句，不要用"尽量""确认后"这种软词
4. 完成判定放在代码里查状态，不要放在提示词里问模型

## 边界

约束太密会让模型束手束脚、反复求助。这套做法适合有明确外部事实可查的场景（有没有提交、测试过没过、来源是哪天）；纯创作类任务用不上，硬套只会把输出写死。
